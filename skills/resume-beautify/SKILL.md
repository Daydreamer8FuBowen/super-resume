# Resume Beautify

本技能是 SuperResume 工作流中的简历美化器。负责：加载基础档案 → 分析 JD 匹配 → 定位决策 → 内容美化 → 写入目标简历 JSON。

`resume-beautify` = **定位决策 + 内容美化 + 持久化**。它是上游信息（基础档案、调研、审查）汇聚后真正产出投递简历的技能。

## When to Use

- SuperResume 工作流调度「美化/写作」节点
- 用户说"帮我针对这个岗位写简历"
- 用户说"根据 JD 美化我的简历"
- 用户说"生成投递版简历"
- 用户提供 JD 并要求定制简历

**不使用：** 编辑基础档案（用 `base-profile-editor`）、调研公司/JD（用 `research-launcher`）、审查已有简历（用 `resume-review`）、预览简历（用 `resume-visual`）、用户只问"这份简历怎么样"但不要求修改。

## Capability Boundaries

### 做的事

1. **加载基础档案** — 通过 `profile-loader` 读取 `data/profiles/base.json`
2. **定位决策** — 根据目标岗位/JD 自行决定：项目排序、技能取舍与排序、Headline/Summary 重写方向、经历保留/合并/弱化
3. **内容美化** — 对选中内容进行 bullet 改写：关键词植入、结果导向表达、动词优化、术语对齐 JD、**上下文扩展**
4. **写入 target JSON** — 通过 `profile-loader` 的 `profile-store.mjs` 小 patch 合并工具写入 `data/profiles/targets/<company>-<role>.json`
5. **输出决策摘要** — 列出做了什么选择及理由

### 不做的事

| 不做 | 应该用 |
|------|--------|
| 修改 `base.json`（不污染事实源） | `base-profile-editor` |
| 凭空编造经历、公司、角色、时间 | — 这些核心事实不可变 |
| 浏览网页做调研 | `research-launcher` |
| 审查已有简历质量 | `resume-review` |
| HTML 渲染 | `resume-visual` |
| 导出 PDF | `resume-visual`（浏览器打印） |

### 关键约束

- **核心事实不可变**：公司名、角色、在职时间、学历——这些核心身份事实不可改变，必须可追溯到 `base.json`
- **任务细节可扩展**：在核心事实框架内，基于 JD 要求 + 公司业务背景 + 行业常识，可以对项目任务细节进行**适度扩展**。扩展必须满足：有逻辑推导链、不违反已有事实、扩展部分标注 `confidence: "inferred"`
- **JD 是锚点**：所有定位决策和扩展方向必须能回溯到 JD 中的要求或调研报告中的公司/行业信息
- **指标优先真实**：优先使用 `base.json` 中的真实数据；在有调研报告或行业常识支撑时，可以合理估算并标注为推断值；无任何依据时在 `notes_for_resume_writer` 中建议补充
- **先分级再写作**：每个强 claim 先标注 `claim_level`、`truth_status` 和 `interview_risk`。`C3` 影响类 claim 没有指标证据时必须降级或写入 `safe_wording`。

## The Process

严格顺序的 5 步流程。不可跳过，不可并行。

```
阶段 1：加载 ─→ 阶段 2：分析 ─→ 阶段 3：定位 ─→ 阶段 4：美化 ─→ 阶段 5：写入
```

### 阶段 1：加载上下文

从上下文和用户输入中收集必要信息。

**必须输入：**

| 输入 | 来源 | 缺失处理 |
|------|------|----------|
| 基础档案 | `profile-loader` 读取 `data/profiles/base.json` | 停止，要求先用 `base-profile-editor` 创建 |
| 目标岗位 | 上下文或用户输入 | 停止，向用户提问 |
| 目标 JD | `research-launcher` 产出或用户粘贴 | 停止，向用户提问 |

**可选输入：**

| 输入 | 来源 |
|------|------|
| 目标公司 | 上下文或用户输入 |
| 公司/行业调研报告 | `research-launcher` 产出 |
| 简历审查报告 | `resume-review` 产出 |
| 用户额外约束 | 用户直接指令（如"突出 AI""用英文""一页"） |

**加载规则：**

1. 调用 `profile-loader` skill 读取 `data/profiles/base.json`
2. 从上下文提取目标岗位、JD、公司名
3. 如有调研报告和审查报告，一并加载
4. 缺必须输入 → 停止并提问；缺可选输入 → 继续
5. 不编造任何信息填充缺失字段

### 阶段 2：分析匹配

内部分析（不对外输出，为阶段 3 定位决策提供依据）。

**JD 关键词提取：**

从 JD 中提取以下维度的关键词和信号：

| 维度 | 提取内容 |
|------|----------|
| 技术关键词 | 编程语言、框架、工具、平台、数据库 |
| 经验要求 | 年限、项目类型、业务领域、团队规模 |
| 软技能信号 | 沟通、协作、领导力、ownership |
| 业务领域 | 电商、SaaS、金融、AI、企业服务等 |
| 隐性偏好 | "有从零到一经验""有高并发经验""有开源项目"等 |

**扩展信号提取：**

从公司/行业调研报告中提取可用于任务细节扩展的上下文信号：

| 信号来源 | 扩展用途 |
|----------|----------|
| 公司技术栈 | 推断项目可能用到的技术生态（如公司用 Spring Cloud → 项目可能涉及微服务治理） |
| 公司业务规模 | 推断项目的业务量级（如电商平台日均百万订单 → 支付系统可能处理高并发） |
| 行业通用实践 | 推断项目的工程细节（如 SaaS 行业 → 项目大概率涉及多租户、RBAC） |
| 公司产品方向 | 推断项目解决的问题类型（如协作工具 → 项目涉及实时同步、冲突解决） |

**交叉对比：**

将 JD 关键词与 `base.json` 进行交叉对比：

- 哪些技能命中 → 标注为突出项
- 哪些项目与 JD 相关 → 标注匹配度（完全匹配 / 部分匹配 / 不匹配）
- 哪些经验对口 → 标注强化方向 + **可扩展方向**
- 识别缺口：JD 要求但 base 没有的 → 分两类——
  - **可通过扩展填补**：JD 关键词与 base 项目技术栈相近，可适度扩展任务描述来覆盖
  - **确实无依据**：记录到 `adaptation_notes`，不编造

**输出（内部）：** 匹配分析结果 + 扩展信号清单，直接用于阶段 3 决策和阶段 4 美化。

### 阶段 3：定位决策

基于阶段 2 的匹配分析，做出以下决策。决策内容直接写入 target JSON，同时在对话中呈现决策摘要。

#### 3.1 项目排序与取舍

按匹配度排序，最相关的放最前面：

| 匹配度 | 判定标准 | 处理 |
|--------|----------|------|
| 完全匹配 | 技术栈 + 业务领域都匹配 JD | 最高优先级，强化为第一个项目 |
| 部分匹配 | 技术栈或业务领域之一匹配 JD | 保留，排序靠前 |
| 弱匹配 | 技术栈和业务领域都无关 | 末尾或考虑移除 |
| 通用项目 | 看不出 JD 信号关联 | 合并为一行或移除 |

**原则：** JD 越具体，项目选择越聚焦。JD 通用则保留 3-5 个匹配度最高的项目。不相关且陈旧的项目移除。每个移除决定记录原因。

#### 3.2 技能取舍与排序

```
JD 明确要求的技能 → 最前面，突出展示
JD 相关生态技能 → 保留，正常位置
与 JD 无关技能 → 末尾或移除
```

**绝不移除**被选中项目中出现的技能。

#### 3.3 Headline 与 Summary

**Headline 公式：**

```
<JD 中的角色关键词> | <最强匹配技能> | <base 中的关键差异点>
```

示例：`"前端开发工程师 | React + TypeScript | 3 年 SaaS 产品经验"`

**Summary 结构（2-3 句）：**

1. 第一句：角色定位 + 经验年限
2. 第二句：与 JD 最相关的 1-2 个核心能力
3. 第三句（可选）：与公司/领域相关的差异点

#### 3.4 经历强化方向

为每个保留的经历/项目确定改写重点：

| Bullet 类型 | 判定标准 | 处理 |
|-------------|----------|------|
| 技术匹配型 | bullet 提到的技术出现在 JD 关键词列表中 | 注入 JD 术语，对齐写法 |
| 结果可量化型 | bullet 描述了可量化的产出（性能、效率、用户量等） | 补充具体指标，无数据则标注 `[需量化]` |
| JD 无关型 | bullet 涉及的技术/业务不在 JD 范围内 | 弱化为一句话或删除 |
| 核心职责型 | bullet 描述的角色职责与 JD 要求一致 | 保留并强化，用 JD 语言重新表述 |

**原则：** 优先改写技术匹配型和核心职责型 bullet。每个保留项至少保留 3 个 bullet，至多 6 个。

#### 3.5 教育/证书/奖项取舍

- 应届/1-3 年经验：教育保留在前
- 3 年以上：教育简要保留在后
- 证书/奖项与 JD 相关则保留，不相关可移除

#### 3.6 输出决策摘要

定位完成后，向用户呈现：

```markdown
## 定位决策摘要

**目标：** <company> - <role>
**匹配度：** <高/中/低>
**Headline：** <new headline>

**项目排序（Top 3）：**
| 排序 | 项目 | 匹配度 | 理由 |
|------|------|--------|------|
| 1 | ... | ... | ... |

**技能策略：**
- 突出：<highlighted skills>
- 弱化：<downplayed skills>

**内容操作：**
- 保留 <N> 个项目
- 合并 <N> 项
- 弱化 <N> 项
- 移除 <N> 项（<移除原因>）
```

### 阶段 4：内容美化

对阶段 3 选中的每个内容项进行 bullet 改写。严格按 5 条规则执行，每条规则配有示例。

#### 规则 1：关键词植入

JD 中的术语自然融入 bullet，不堆砌关键词。

```
❌ "使用 React 和 TypeScript 开发前端页面，用 Webpack 打包，用 Jest 测试"
✅ "使用 React + TypeScript 重构商品管理模块，构建可复用的设计系统组件库"
```

#### 规则 2：结果导向

有量化指标用指标，没指标强调解决的具体问题或带来的改变。

```
❌ "负责优化了页面加载速度"
✅ "将首屏加载时间从 3.2s 降至 1.1s，LCP 提升 65%"
```

无指标时同样适用：

```
❌ "参与了订单系统的开发"
✅ "实现了订单状态机与支付回调的端到端流程，消除了超时丢单问题"
```

#### 规则 3：动词升级

弱动词 → 强动词，体现个人贡献。

| 避免 | 使用 |
|------|------|
| 参与了 | 主导 / 负责 / 实现 / 构建 |
| 协助了 | 独立完成 / 推动 |
| 做了 / 写了 | 设计并实现 / 重构 / 优化 |
| 负责日常... | 删掉（无信息量，或用具体成果替代） |

```
❌ "参与了微服务拆分项目"
✅ "主导订单模块从单体到微服务的拆分，设计了 7 个独立服务"
```

#### 规则 4：删除空泛

删除没有信息量的描述，每个 bullet 必须传递一个具体信号。

```
❌ "负责日常开发工作和代码 review"（空泛）
✅ "制定团队 ESLint 规范，Code Review 覆盖率从 30% 提升到 95%"（有信号）
```

#### 规则 5：术语对齐

技术名称写法和 JD 保持一致。

```
JD 写 "React" → 不要写 "React.js"
JD 写 "PostgreSQL" → 不要写 "Postgres" 或 "PG"
JD 写 "机器学习" → 不要写 "Machine Learning"（中文 JD 用中文术语）
```

#### 规则 6：上下文扩展

基于 JD 要求 + 公司业务背景 + 行业常识，对项目任务细节进行**适度扩展**。扩展并非凭空编造——它是从已有事实出发的逻辑延伸。

**扩展三要素（缺一不可）：**

| 要素 | 含义 | 示例 |
|------|------|------|
| **事实锚点** | base.json 中的已有事实作为起点 | "开发了订单支付模块" |
| **外部信号** | JD 要求 或 公司业务 或 行业常识 | JD 要求"高并发系统经验"，公司是电商平台 |
| **逻辑推导** | 从事实 + 信号到扩展内容的推理链 | 电商支付 → 必然涉及高并发 → 可扩展描述并发处理能力 |

**允许的扩展：**

```
base.json: "负责订单服务的后端开发，使用 Spring Boot + MySQL"
JD 信号: "有分布式系统设计经验"
公司调研: 公司核心业务为电商，日均订单量百万级

✅ 合理扩展:
"设计并实现了订单核心服务，基于 Spring Boot 微服务架构，
通过 Redis 缓存 + 数据库读写分离应对日均百万级订单查询，
优化慢 SQL 将核心接口 P99 延迟从 800ms 降至 120ms。"
→ 微服务架构、Redis 缓存、读写分离、性能优化——
  都是从"后端开发 + 电商"可逻辑推导的工程实践。
→ confidence: "inferred"
```

**禁止的扩展（凭空编造）：**

```
❌ "带领 5 人团队完成订单系统从零到一的搭建"
   → 没有事实锚点（团队规模、从零到一都是编造）

❌ "系统上线后为公司节省 200 万人力成本"
   → 量化指标无任何依据

❌ "获得公司年度最佳技术项目奖"
   → 奖项是编造的事件
```

**扩展分级：**

| 级别 | 定义 | Confidence 标注 | 示例 |
|------|------|-----------------|------|
| L0: 纯改写 | 只改表达，不扩展内容 | `high` | 动词升级、术语对齐 |
| L1: 技术推断 | 从已有技术栈推断相关技术实践 | `medium` | Spring Boot → 微服务、Redis 缓存 |
| L2: 业务推断 | 从公司/行业推断业务场景和规模 | `inferred` | 电商公司 → 高并发、分布式事务 |
| L3: 禁止 | 无事实锚点或逻辑链断裂 | 不写入 | 编造指标、团队、奖项 |

**规则：**
- L1 和 L2 扩展必须有至少一条外部信号（JD 关键词 / 公司业务 / 行业常识）作为依据
- 每个扩展 bullet 在 `fact_traceability` 中标注 confidence 级别
- 如果无法判断扩展是否合理，采用保守策略——不扩展，标注建议

#### 美化产出

为每个保留项产出改写后的 bullet 列表，填入 `tailored_content`：

- `headline` — 根据阶段 3.3 公式撰写
- `summary` — 2-3 句概述
- `experience_bullets` — 每个工作/实习经历的改写 bullet
- `project_bullets` — 每个项目的改写 bullet
- `skills_section` — 重组的技能展示
- `notes_for_resume_writer` — 建议补充的指标/信息

### 阶段 5：写入并总结

1. 创建最小 target patch JSON，只包含本次生成或更新的字段
2. 调用 `node skills/profile-loader/profile-store.mjs merge --profile target --id <company-role> --patch <patch.json>`
3. 使用 `profile-loader` 的 target profile schema，填充所有字段
3. 为每个 `tailored_content` 中的 claim 填入 `fact_traceability`：
   - 直接改写项 → `source_section` + `source_id` + `confidence: "high"`
   - 技术推断项 → `source_section` + `source_id` + `confidence: "medium"` + 推断逻辑
   - 业务推断项 → `source_section` + `source_id` + `confidence: "inferred"` + 依据信号
   - 同时填入 `claim_level`、`truth_status`、`safe_wording`、`interview_risk`
4. 若目标文件已存在且本次不是明确迭代更新，询问用户：覆盖 / 创建带日期的版本 / 取消

**禁止**直接手写并替换整个大型 target JSON。Agent 只负责准备小 patch；合并、格式化、原子写入和校验交给 `profile-store.mjs`。

**输出格式：**

```markdown
已生成目标简历。

**写入：** `data/profiles/targets/<company>-<role>.json`

## 定位决策摘要

**目标：** <company> - <role>
**Headline：** <new headline>

**项目排序：**
| 排序 | 项目 | 匹配度 | 理由 |
|------|------|--------|------|
| ... | ... | ... | ... |

**技能策略：** 突出 <N> 项 / 弱化 <N> 项
**内容操作：** 保留 <N> 项 / 合并 <N> 项 / 移除 <N> 项

## 下一步
- 预览效果：`/resume-visual`
- 需要调整：告诉我具体改什么，例如"把 xx 项目放第一个"
```

## Error Handling

| 场景 | 处理 |
|------|------|
| `base.json` 不存在 | 停止。提示用户通过 `base-profile-editor` 创建 |
| `base.json` 几乎为空 | 警告用户，继续但标注结果会很薄 |
| JD 无关键词可提取 | 以目标岗位名为最小信号，标注不确定性。仅做 L0 美化，不做扩展 |
| 无调研报告/公司信息 | 不阻塞。只能做 L0 和 L1 扩展（技术推断），不能做 L2 扩展（业务推断） |
| JD 要求与 base 事实矛盾 | 不改变核心事实。在 `adaptation_notes` 中记录差距 |
| 用户约束与 JD 信号冲突 | 用户约束优先，在摘要中注明权衡 |
| 扩展方向不确定 | 保守处理——不扩展。在 `notes_for_resume_writer` 中标注："此处可扩展：<方向>，需用户确认" |
| 目标文件已存在 | 询问：覆盖 / 创建版本副本 / 取消 |
| Profile 有 10+ 项目，JD 通用 | 保留 Top 3-5，其余放入"其他项目" |
| 中英混杂（中文 JD vs 英文 base 或反之） | 输出语言对齐 JD 语言，保留关键双语术语 |

## Anti-Patterns

| 禁止 | 正确做法 |
|------|----------|
| 修改 `base.json` | 始终只写入 `targets/` |
| 凭空编造核心事实（公司、角色、时间、学历） | 核心身份事实不可变 |
| 无依据编造量化指标（"提升 200%""节省 500 万"） | 优先用真实数据；有行业常识支撑时可合理估算并标注 `inferred` |
| 扩展无逻辑链（"开发登录页" → "设计高可用分布式认证系统"） | 扩展必须有事实锚点 + 外部信号 + 逻辑推导 |
| 删除项目不记录原因 | 在 `adaptation_notes` 中记录理由 |
| 关键词堆砌 | 自然、上下文相关的关键词放置 |
| 所有岗位用同一 headline | 每次从 JD 重新推导 |
| 跳过 `fact_traceability` | 每个 claim 必须可追溯，扩展项标注 confidence |
| 无证据写 C3 结果影响 | 降级为过程/分析表述，或放入 `safe_wording` 等待补证据 |
| 不确定扩展偷偷执行不告知 | 在决策摘要中标明扩展项及依据 |
